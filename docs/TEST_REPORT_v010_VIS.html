3. arcli 已解决的问题

实验命名与组织 解决度 95% ▾

原始问题: 11 个实验目录命名随意，无法从名称推断目的。

arcli 方案: run-{short_id}-{TIMESTAMP}_{label} 格式，语义化标签 + 自动编号。

剩余问题: 实验目录内的子目录仍由脚本自行管理（如 run-003-suite/run_20260501_130446/exp_01_baseline_d1000000），arcli 未约束。

代码版本绑定 解决度 100% ▾

原始问题: 不知道实验跑的是哪版代码。

arcli 方案: experiment.json 自动记录 commit_hash。

{
  "id": "run-001-2026-05-01-1304_baseline-smoke",
  "commit_hash": "bffebbb38cbb10874a7cdf96cdfa49810ddedee6",
  "command": "python3 -m src.run --csv results.csv",
  "status": "finished",
  "exit_code": 0
}

效果: 任何时候都可以通过 git checkout <commit_hash> 精确复现实验环境。

失败实验追溯 解决度 100% ▾

原始问题: 实验失败时 stdout 丢失，无法定位原因。

arcli 方案: experiments/{id}/logs/run.log 完整捕获 stdout/stderr。

案例: 实验3（full-suite-smoke）因 CSV 字段不匹配失败：

$ arcli log show run-003-... --tail 5
[stdout] dp lambda=1.0 completed in 0.03s
# ValueError: dict contains fields not in fieldnames: 'x_prev'

配合 commit_hash 和 exit_code: 1，可立即定位到 exp_runner.py:192 的 Bug。

工作区清洁度检查 解决度 90% ▾

方案: exp new 强制检查 git status，不干净时报 WORKSPACE_NOT_CLEAN。

问题: 检查过于严格。实验运行后产生的 timeline_*.csv 被标记为 untracked，导致下一个 exp new 失败。

数据资产管理 解决度 85% ▾

方案: arcli data register 记录名称、路径、SHA256 校验和、描述。

问题: 数据资产变更后需要手动 data update，没有自动检测文件变化。

双轨持久化 解决度 90% ▾

方案: SQLite（查询）+ JSON（版本控制）双轨同步。

$ arcli db status
已同步: ["run-003-...", "run-002-...", "run-001-..."]

4. arcli 未解决的问题

P0 · 实验输出路径引导 严重缺失 ▾

现象: run.py 默认在仓库根目录写 timeline_*.csv，污染工作区。

影响: 每次实验后根目录出现 untracked 文件，下一次 exp new 失败。

根因: arcli 没有向实验脚本传递"当前实验目录"信息。

改进: 注入 $ARCLI_EXP_DIR 环境变量，或提供 arcli exp artifact add。

P0 · 历史实验迁移 功能缺失 ▾

现象: 原始工程 11 个历史实验目录（含数百个 PNG/CSV）无法纳入 arcli 管理。

改进: 增加 arcli exp import <DIR> --cmd <CMD> --label <LABEL>。

P1 · 实验超时控制 功能缺失 ▾

现象: DP 求解器可能运行数小时，exp run 没有 --timeout。

改进: exp run --timeout 3600 超时后 SIGTERM + 标记 interrupted。

P1 · 参数 diff 追踪 功能缺失 ▾

现象: 实验2修改了 params.py 中的 K_r_i，但 experiment.json 未记录参数差异。

改进: exp new 时自动记录 git diff 到 experiment.json 的 diff 字段。

P1 · Hook 强制检查过严 体验问题 ▾

现象: .research/hooks 必须至少有一个文件，否则 exp new 失败。

改进: project init 时生成默认 hook 说明文件，或降低严格度。

P1 · --json 标志位置 解析问题 ▾

现象: arcli exp list --json 报错，必须写成 arcli --json exp list。

改进: 在每个子命令也声明 --json 别名。

7. 结论

核心解决（完全达标）

实验命名规范化、代码版本绑定、失败追溯三个维度完全解决了原始工程的核心痛点。双轨持久化和数据资产管理提供了远超"文件夹管理"的可靠性。

明显缺口（需要 v0.2.0）

实验输出路径引导、历史迁移、超时控制三个维度存在明显缺口。对于长周期、多迭代的研究工程（如本案例），这些缺口会成为严重瓶颈。

总体评价

arcli 将研究工程的可复现性从"靠运气"提升到了"靠机制"。对于 3-5 人团队、10-50 次实验迭代的研究项目，arcli v0.1.0 已具备实用价值。对于更复杂的工程（如 MCM2026），需要 v0.2.0 的 exp import、--timeout 和 artifact 索引能力。
